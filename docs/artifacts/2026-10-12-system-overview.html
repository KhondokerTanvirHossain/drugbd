The big picture

Data flows one way, from public sources through the pipeline into PostgreSQL. The API reads it, and the website shows it. Pharmacists' decisions flow back through the website into the review tables, and the API uses those tables to decide what the public may see.

ETL pipeline: bddrug-etl

One Python 3.12 package with one command. It runs up to four stages for one batch file, always in the order dgda → substances → clinical → ddinter, and each stage commits on its own. Each product runs in its own savepoint, so one failing product never stops the others. A lost database connection stops the stage. Every run is appended to ops.batch_run, and the run ends with a log line such as batch=0001-pilot dgda=10/0/0 substances=10/0/0 clinical=10/0/0 ddinter=0/10/0 (ok/warn/fail counts).

stage 1 · dgda

Load the registered product

Fetches each concept in the batch file from the national OCL server and loads the product and its ICD-11 ingredients.

Calls
OCL GET /orgs/MoHFW/sources/DGDA-Drugs/concepts/{id}/, with a 0.5 s pause and a 60 s timeout
Writes
raw.ocl_concept, brand_product, brand_product_ingredient, ops.batch / batch_item
Results
ok · fail “not found at source” · fail “not a registered Drug product”
stage 2 · substances

Identify the active ingredients

Finds or creates one BDS- substance per ICD-11 XM code. It records names (for example, Paracetamol for Acetaminophen) and adds RxNav codes.

Calls
RxNav rxcui.json, approximateTerm.json, properties, allProperties?prop=codes, at most 10 requests/s
Writes
substance, substance_name, substance_code (XM, RXCUI, ATC, DRUGBANK, SNOMEDCT), raw.http_snapshot
Results
ok · warn “no RxCUI for …” · fail “no ICD-11 ingredient mapping”
stage 3 · clinical

Strength, form and route

Parses the strength text (for example “Amoxicillin + Clavulanic Acid 500 mg + 125 mg”), matches each strength to its substance by name, and links the product to a shared BDC- clinical drug.

Calls
None (pure parsing)
Writes
clinical_drug, clinical_drug_ingredient, brand_product.bdc_id / parse_status
Results
ok · warn (partial parse, unaligned ingredient, substance missing from the text) · fail (unparseable)
stage 4 · ddinter

Interactions

Maps each substance to its DDInter entries, taking route into account and confirming the match by DrugBank ID. It stores the substance’s drug–drug pairs, disease and food records and interaction texts, and records explicit coverage (“none” for domperidone).

Calls
DDInter drug list, drug detail, pair graph, interact-with lists, interaction pages, at most 1 request/s with CSRF handled
Writes
ddinter_* tables, substance_code (DDINTER), interaction_coverage, raw.http_snapshot
Results
ok · warn (name-only match, no DDInter data, text not found) · fail. Commits every --ddinter-chunk products.

DDInter pairs and texts never re-open a record. A new item of a product approved in another batch with the same view is carried approved. Shared substance changes re-open other records only when their view changed.load/batches.py

API: bddrug-api

Java 21, Spring Boot WebFlux with R2DBC, in a hexagonal layout. It runs only on the internal Docker network and is never reachable from the internet. Every response uses the standard envelope {success, data, message, errors, metadata}. A request without the internal token gets public scope: only records a pharmacist approved. With the token, which only the web server holds, a request gets all scope and can write.

Rules inside the API

Approval gate (ApprovalRule, ReviewSql): a record is public only after a pharmacist records OK after its latest extraction, with no issue recorded after that OK. An engineer’s OK is recorded but does not publish. Route rule (RouteRule): an eye-drop product uses the ophthalmic DDInter entry when one exists; otherwise the alert says the route was assumed. Hidden records (HiddenRecord): “not yet reviewed” is never shown as “not found” or “no data”. Startup: the API refuses to start without a strong internal token (at least 32 characters). Validate: shared input checks for every write.

Website: bddrug-web

Next.js 15 with every page rendered on the server. The only browser-side code is the Google sign-in button. The web server calls the API privately and attaches the internal token only for reviewers and for writes.

Deployment and CI

Three images (bddrug-etl, bddrug-api, bddrug-web) are built by GitHub Actions, tagged with the commit hash and stored in GHCR. They run with docker-compose on the shared EC2 host in /home/ec2-user/drugdb, next to medscribe and n8n. The existing Caddy handles HTTPS for drugdb.eliooo.org. No host ports are published, and only the website is on Caddy’s network.

How to do common things

Load a new batch

  1. Add batches/NNNN-name.txt (one OCL concept ID per line) in a PR.
  2. Merge. The deploy copies the file to the host.
  3. In the Actions tab, run load-dgda with batch=NNNN-name.txt.
  4. Reviewers open /batches/NNNN-name.

Re-run one record

  1. On the host, run:
cd ~/drugdb/deploy
docker-compose --profile jobs run --rm etl \
  --batch /app/batches/0001-pilot.txt \
  --concept 186-0030-006--napa

The record goes back to pending and must be reviewed again.

Add or remove a reviewer

  1. On the host, edit the REVIEWERS= line in ~/drugdb/deploy/.env (email:pharmacist,email:engineer).
  2. Run docker-compose up -d --no-deps web. Only the website restarts.

Change the database

  1. Never edit V1–V5.
  2. Add db/migrations/V6__what.sql and its checksum line in db/migrations.lock.
  3. Explain the change and its rollback in the PR. CI schema-lock enforces the rest.

Known gaps and notes

These came out of reading the code against the docs. None of them breaks anything today.

By designBatch pages and their API endpoints are public, including extracted data and raw DGDA JSON for records not yet approved. They are evidence pages; the approval gate applies to search, product, substance and the checker.
By designThe API uses /v1/… rather than the platform’s usual /api/v1/…. It is internal-only, behind the website.
To tidyThe workflow name load-dgda is historical: it runs the full pipeline. It doesn’t yet expose --concept, --stages or --ddinter-chunk; those need SSH for now.
To tidyThe legacy jobs/load_dgda.py module is no longer used and can be removed.
To tidyNo container health checks are defined for api and web. restart: unless-stopped recovers crashes, but a hung process would go unnoticed.
To tidyThe rate limiter keeps its counts in memory, which works because the site runs one web container. It needs a shared store if it ever scales out.
DocsThe README intro still describes Sprint 1, and a compose comment says the ETL network is “for OCL only” (it also reaches RxNav and DDInter). Both need updating.
DocsDeferred minor items from each sprint’s reviews are listed in docs/superpowers/plans/*-execution-ledger.md.
