Database design · for verification

BDDrug KB data model

How the Bangladesh drug knowledge base is stored in PostgreSQL. It covers the brand, clinical drug and substance levels, the crosswalk codes, the DDInter interaction mirror, and the evidence and review tables behind the approval gate.

Schema as of 12 Oct 2026 Migrations V1–V8 (V8, db-schema-v1.3, adds the qa_read audit event) PostgreSQL 16 Row counts: live pilot (10 medicines)

Three schemas, 24 tables

Data moves one way. Source responses are stored verbatim in raw. They are interpreted into the drug master and interaction knowledge in curated. Every pipeline run, review decision and flag is recorded in ops, and the public site only shows curated records whose ops review is approved.

Diagram 3 · Evidence, batches and review

Every record enters through a batch. Each pipeline stage writes one result per record with its evidence. Review decisions are append-only, and the approval gate reads them together with batch_item.extracted_at, so a re-run automatically puts a record back into review.

raw.http_snapshot (source, request_key) → status, body, fetched_at sits beside these tables with no links. It keeps every RxNav and DDInter response, with CSRF tokens redacted, so each code and interaction can be traced to the exact response that produced it.

Rules the schema enforces

These rules are enforced by database constraints, so the data cannot break them whatever the application code does.

One substance per ICD-11 XM code

A partial unique index on substance_code(code) WHERE system = 'ICD11_XM'. DGDA maps every product to salt-free XM substances, so Warfarin Sodium and Warfarin share one substance.

substance_code_xm_unique

Permanent, bounded IDs

BDS- and BDC- come from sequences capped at 999,999 with NO CYCLE. Re-runs look up existing IDs before minting, so an ID is never reused or renumbered.

curated.bds_seq · curated.bdc_seq

Same strength and form, same clinical drug

clinical_drug.signature is unique: dose form, route and the sorted strengths. Two brands of paracetamol 500 mg tablet share one BDC.

clinical_drug.signature UNIQUE

Route-aware interactions

A DDINTER code carries a route_scope. An eye-drop product uses the ophthalmic DDInter entry when one exists; otherwise the alert is marked “route assumed”.

substance_code.route_scope

“No data” is stored, not implied

interaction_coverage holds full or none per substance. Domperidone is none, so the site can say “no interaction data”, never “no interactions”.

interaction_coverage.coverage

Missing text is NULL, never a placeholder

Interaction texts may be NULL, but a text row needs at least one of interaction or management. DDInter’s “None” is stored as missing.

ddinter_interaction_text_has_text

Each pair stored once

ddinter_pair requires ddinter_a < ddinter_b, so A–B and B–A cannot both exist.

CHECK (ddinter_a < ddinter_b)

Review history cannot be deleted

review_decision references batch_item with ON DELETE NO ACTION, so a reviewed record cannot be removed. Decisions are only ever inserted.

review_decision → batch_item (NO ACTION)

Snapshots and the audit trail are append-only

Triggers reject UPDATE, DELETE and TRUNCATE on item_snapshot and audit_event. A batch item with a snapshot cannot be deleted, so an item that leaves the batch file is kept and marked “removed from batch file”.

ops.reject_change() triggers

A re-run re-opens only what an approval covers

The pipeline's settle() compares each record's approval view (brand fields, clinical drug and, per ingredient, substance, strength, codes, chosen DDInter entries and coverage) with the view in its snapshot. Only a changed view stamps the record pending; DDInter pairs, texts and entry names never re-open it. A new item of a product approved in another batch with the same view carries that approval (carried_from in its snapshot). settle() locks batch_item rows before the batch row, the same order as the API's decisions.

load/batches.py settle · snapshots.approval_view

Pair reviews are append-only and keep what they reviewed

A senior pharmacist's pair decision stores the pair's content and its hash, so the API can tell when DDInter changed a reviewed pair. Triggers reject UPDATE, DELETE and TRUNCATE on pair_review.

pair_review, ops.reject_change() triggers

Confidence and enums are checked

Confidence must be 0–1. Code systems, severities, stages, review states and roles are restricted by CHECK constraints.

CHECK constraints

The approval gate

The approval gate is computed from data rather than kept as a flag. The API derives each record’s state on every public read.

OK (public)
A pharmacist recorded ok after the record’s latest extracted_at, and nobody recorded issue after that.
Issue
The latest decision since extraction is issue.
Pending
Anything else: no decisions yet, only an engineer’s ok, or decisions made before a re-run.
Batch approved
Every record in the batch is OK.
Re-open
A pipeline run that rewrites a record, or changes shared substance data it uses, moves extracted_at forward. Earlier approvals stop counting, and the history stays.

Compared with the original design

BuiltBrand → clinical drug → substance, crosswalk codes with provenance, synonyms, route-aware DDInter mapping, coverage, drug–drug / disease / food tables, evidence per stage, append-only review.
ChangedInteractions are mirrored in DDInter’s ID space and joined through codes, instead of a ddi table keyed on our substance pairs. This lets partner drugs we haven’t loaded yet still show by name.
Changedreview_task was replaced by review_decision plus a computed approval state on batch_item.
ChangedSubstances are keyed on DGDA’s ICD-11 XM codes. Salts are already resolved there, so salt_form has not been needed yet.
PlannedMonthly release snapshots (versioned, read-only copies for partners), partner API keys and usage metering, a gold test set of known interactions, packs and MRP.

Worth checking while you review

  1. Substance identity. One substance per ICD-11 XM code works when DGDA’s mapping is right. Should a pharmacist be able to merge two substances if DGDA ever splits one ingredient across two codes?
  2. Interactions at substance level. Interactions attach to the substance (and route), not to strength or brand. That is standard for checkers, but confirm it is acceptable clinically.
  3. Same substance twice in one product. clinical_drug_ingredient allows a substance only once per clinical drug. If a product lists the same base substance twice (two salts), the pipeline warns and creates no clinical drug.
  4. Approval granularity. Approval is per record (brand). An approved record goes back to review only when its approval view changes, which a shared substance change made in another batch can do. DDInter pair and text updates never re-open it, and a product approved in one batch carries its approval to a new batch when its view is unchanged. Check that this re-review load stays acceptable as batches grow.
  5. Personal data. Reviewer and reporter emails are stored in ops only and never served publicly. Decide how long they should be kept.
